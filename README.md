# AVsentry

**AI-Based Smart Room Safety & Environmental Monitoring System**
A TinyML / Edge AI capstone project — multi-sensor reasoning for intrusion
detection and environmental discomfort, running entirely on a NodeMCU
ESP8266 with no cloud dependency for its core logic.

---

## What it does

AVsentry watches a room using two sensors — a DHT11 (temperature/humidity)
and a passive-IR sensor (presence) — and classifies the current situation
into one of five states using a machine-learned decision tree running
**on-device**:

| Class | Meaning |
|---|---|
| `normal` | Ambient conditions, no presence |
| `discomfort_hot` | Temperature above threshold |
| `discomfort_humid` | Humidity above threshold |
| `occupied_uncomfortable` | Presence detected during poor conditions |
| `intrusion` | Presence detected under otherwise normal conditions |

Based on the predicted class, it drives a buzzer, two status LEDs, and a
servo — and optionally serves a live dashboard on the local network.

## Why this counts as Edge AI / TinyML

Training happens **once, offline, on a laptop** (see `/training`). The
trained model is compiled into plain C (`model.h`) and embedded directly
in the firmware. At runtime, the NodeMCU alone reads sensors and runs
`predict()` — nested if-else logic, no ML runtime library, no network
call required. The laptop is not involved once the firmware is flashed.

A TensorFlow Lite Micro approach was considered and rejected: the
ESP8266 has roughly 50KB of usable RAM and no FPU, making a full TFLite
Micro runtime impractical here. A shallow scikit-learn Decision Tree,
compiled via [micromlgen](https://github.com/eloquentarduino/micromlgen),
gives a genuinely learned multi-feature decision boundary at a fraction
of the footprint.

## Hardware

| Component | Pin | Notes |
|---|---|---|
| NodeMCU ESP8266 | — | Runs sensing + inference + actuation |
| DHT11 | D4 | Temperature & humidity |
| IR obstacle sensor | D7 | `0` = detected, `1` = clear |
| Passive buzzer | D1 | Driven with `tone()`/`noTone()` |
| Green LED | D0 | Lit when `normal` |
| Red LED | D5 | Lit for any non-normal class |
| Servo motor | D2 | Swings on `intrusion`; powered from the 3.3V rail, **not** Vin |

## Building it yourself

### 1. Collect data
Flash a stripped-down version of the sketch that only prints
`temp,humidity,ir` over Serial each cycle (remove the model/actuator
logic from `AVsentry.ino` for this step). Then, per scenario:

```bash
cd training
pip install -r requirements.txt
python log_data.py
```

Choose the scenario being simulated when prompted; run once per class,
appending to `sensor_log.csv` each time.

### 2. Clean and train

```bash
python clean_data.py
python train_model.py
python convert_model.py
```

Copy the generated `model.h` into `firmware/`, replacing the placeholder.
**Check the closing braces** — see the comment at the top of
`firmware/model.h` for a known micromlgen quirk.

### 3. Flash the firmware
Open `firmware/AVsentry.ino` in the Arduino IDE (board: *NodeMCU 1.0,
ESP-12E Module*), fill in your WiFi credentials if you want the
dashboard, and upload.

### 4. View the dashboard (optional)
On a device connected to the same WiFi network, visit
`http://avsentry.local` (or the IP address printed in Serial Monitor).
The core sensing/actuation loop works identically with or without WiFi
— the dashboard is a non-blocking bonus layer, not a dependency.

## Model performance

Trained on ~700+ physically staged, labeled sensor readings across the
five classes. Overall test accuracy: **~93%**, with `normal` and
`intrusion` both at 100% precision/recall. Residual confusion sits only
between the two heat-related classes (`discomfort_hot` ↔
`occupied_uncomfortable`), which genuinely share overlapping temperature
ranges — intrusion detection is unaffected.

## Engineering journey — two real bugs, diagnosed and fixed

**The "hour" feature trap.** An early version used time-of-day (via
WiFi + NTP) to distinguish night-time intrusion from daytime presence.
It backfired: the model had only ever seen a few training-time hours,
so real-world hours outside that range caused false intrusion alarms.
*Fix:* dropped the time feature entirely — this also removed the WiFi
dependency from the core logic, improving robustness at any hour.

**Label contamination.** During data collection, presence was toggled
on and off within single labeled sessions (to simulate intermittent
motion), leaving some `intrusion`/`occupied_uncomfortable` rows with the
IR sensor actually reading clear. *Fix:* `clean_data.py`
programmatically filters out every row where the label and the live IR
state disagree, before retraining — this resolved false positives on
normal and humid conditions.

## Future work

- Reintroduce time-of-day context via a lightweight RTC module instead
  of WiFi/NTP, avoiding the earlier failure mode.
- Add gas/smoke sensing for a fuller safety picture.
- Physical enclosure for the breadboard build.
- Push notifications / off-network dashboard access.
